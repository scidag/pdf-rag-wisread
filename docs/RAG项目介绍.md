# 智阅 RAG 项目介绍与问答

> 本文基于智阅（Wisread）当前代码实现撰写。涉及具体参数、流程、限值的描述均以 `backend/src/main/java`、`backend/src/main/resources/application.yml` 和数据库迁移脚本为准。
>
> 全文用“已实现”“当前为占位/未启用”“建议/规划”区分事实与规划。面试或对外介绍时，建议先说当前实现，再补充改进方向。

## 0. 一句话定位

智阅是一个“私有知识库 PDF 智能阅读与问答助手”：用户上传 PDF，系统完成解析、切块、向量化索引，用户基于原文进行多轮问答，回答附带文档名、页码和原文片段引用。

---

## 一、项目概述与业务问题

### 1.1 解决了什么业务问题

长文档的“读、找、核”成本高。论文、技术文档、合同、行业报告通常几十到几百页，用户要定位某个结论、条款、参数时，只能整篇翻找，并且拿到结果后还要再核对出处。

智阅把这一流程压缩为：

1. 上传 PDF，后台自动解析并建立可检索的知识库；
2. 用自然语言提问，系统从文档原文中召回相关片段；
3. 生成回答的同时给出 `[1]`、`[2]` 编号，前端展示文档名、页码、原文片段，用户可以立即核对。

核心价值是“降低长文档阅读成本 + 引用可信”：答案不是黑盒，每句话都能追到原文第几页。

### 1.2 知识库规模与格式

当前是单用户私有知识库 MVP，规模很小：

- 每个项目最多 5 个 PDF（`DocumentService.MAX_DOCUMENTS_PER_PROJECT = 5`）；
- 单个文件上限 100 MB（`DocumentService.MAX_FILE_SIZE`）；
- 单个文档文本量上限 50 万 token（`DocumentProcessingService.MAX_TOKEN_COUNT`）；
- 只支持文字型 PDF，格式通过文件前 4 字节 `%PDF` 校验；
- 更新方式是“文档级更新”：重新上传覆盖或删除后重传，没有在线增量编辑。

这个规模是刻意的：MVP 要验证的是“解析 → 索引 → 问答 → 溯源”闭环是否成立，而不是一开始就做企业级海量知识库。

### 1.3 为什么用 RAG，而不是微调或长上下文模型

三个原因：

1. **知识是动态且私有的**：每个用户上传自己的 PDF，随时增删。RAG 的知识在索引里，换文档只需重建索引；微调要把知识“焊进”模型权重，更新一次训练一次，不现实，还有私有数据泄露风险。
2. **需要可核对的引用**：业务核心是“答案能追到原文第几页”。RAG 天然携带来源 chunk；微调模型只能凭记忆回答，无法给出精确页码。
3. **文档可能超过上下文窗口**：单个文档上限 50 万 token，远超任何单次模型上下文。RAG 每次只把最相关的 3 个切片（每个约 800-1200 token）送入模型，成本和时间都可控。

## 二、数据与索引

### 2.1 文档解析怎么做？表格、扫描件、复杂 PDF 怎么办？

当前实现（`PdfParsingService`）：

- 用 Apache PDFBox 按页提取文本，保留每页页码，输出 `List<PageText>`；
- 加密 PDF 直接拒绝；
- 所有页都提取不到文本（扫描件、纯图片 PDF）直接拒绝，给出“scanned or empty PDF is not supported”。

对表格和复杂排版，当前是明确的能力边界：

- 表格会被 PDFBox 按阅读顺序展平成文本，结构信息（行列）会丢失；
- 扫描件/图片 PDF 不支持 OCR；
- 复杂分栏 PDF 依赖 PDFBox 的文本顺序，顺序异常时切块内容可能错乱。

这是“先跑通闭环、再补格式”的取舍。改进方向是引入 OCR 和版面分析（如 PaddleOCR、Layout Parser），把表格结构转成 Markdown 再入库。

### 2.2 分块策略：chunk size 和 overlap 怎么定的？

实现（`ChunkingService`）：

| 参数 | 值 | 说明 |
|---|---|---|
| 最小切片 | 800 token | 少于这个数不主动切 |
| 最大切片 | 1200 token | 超过这个数且当前块已达最小要求则落盘 |
| 重叠 | 150 token | 取上一块尾部最多 150 token 作为新块开头 |
| 粒度 | 按页 | 每页独立切片，不跨页合并 |

切分流程：

1. 连续空白压成单个空格并 trim；
2. 按句末标点 `。！？.!?` 分句（lookbehind 保留标点）；
3. 贪心累积句子到 800-1200 token 区间，追加前用 `TokenCounter` 估算；
4. 切新块时，用上一块尾部最多 150 token 作为 overlap。

为什么这样定：

- 800-1200 token 对中文文档约等于半页到一页，语义完整且不太碎片；
- overlap 150 token 是为了覆盖“答案恰好横跨切片边界”的情况；
- 按页切片是为了保住页码引用，代价是“一个结论跨两页”时会被拆开。

当前用 `text.length() / 4` 估算 token，不是真实 tokenizer，存在误差；后续可以换成模型同款 tokenizer 或做语义切块。

### 2.3 为什么选这个 embedding 模型？对比过哪些？

当前配置（`application.yml`）：

```yaml
spring.ai.openai:
  chat.options.model: qwen3.7-plus
  embedding.options.model: qwen3.7-text-embedding
```

向量维度 1024（`document_chunks.embedding VECTOR(1024)`），距离用余弦。

选择理由：

- 模型服务（DashScope 兼容 OpenAI 协议）和聊天模型同一家，只维护一套 API Key 和调用链；
- 1024 维在当前数据规模下足够表达语义，pgvector 检索开销可控；
- `embedding_model_version` 字段记录模型标识，换模型前必须重建索引并保证维度一致。

需要诚实说明：当前没有做系统的 embedding 对比实验（如 BGE、text-embedding-v3、OpenAI embedding 在同一评测集上的召回率对比）。这是改进方向，不应在面试里说成“对比过”。

另外有本地 Mock 模式（`LocalEmbeddingModel`，SHA-256 生成确定性 1024 维向量）：用于无 Key 环境跑通全链路和自动化测试，不具备语义能力，生产必须关闭。

### 2.4 向量数据库为什么用 PostgreSQL + pgvector？

没有单独引入 FAISS / Milvus / ES，选择 pgvector，原因：

1. **少一个组件**：文档、会话、消息、引用溯源本来就在 PostgreSQL，向量直接作为 `vector` 列和业务数据同库存储，事务、级联删除、备份一份搞定；
2. **当前规模足够**：单项目最多 5 个文档、每文档最多 50 万 token，HNSW 索引（`USING hnsw (embedding vector_cosine_ops)`）满足毫秒级召回；
3. **部署成本低**：Docker Compose 里一个 postgres 镜像带 pgvector 即可，不引入额外运维面。

什么时候换：知识库到千万级切片、需要分布式扩容、或需要混合检索/图检索等 pgvector 不便承载的能力时，再迁移 Milvus/ES。

## 三、检索策略

### 3.1 检索流程是怎样的？纯向量检索吗？

当前是“查询改写 + 纯向量检索 + 重排取前 3 + 阈值兜底”（`ChatService.processAsk`）：

```
用户问题
  → QueryRewriteService（有历史时用 LLM 改写为独立问题）
  → 问题向量化
  → pgvector 余弦距离召回 Top 10
  → RerankService 取 Top 3
  → 最相似距离 > 0.65 或无结果 → 直接回答“文档中没有找到相关信息”
  → 组装 Prompt 流式生成
```

SQL 按 `user_id + project_id + status='READY'` 过滤，只检索当前用户、当前项目下已就绪的文档。

当前没有混合检索：纯向量检索，没有 BM25/关键词召回融合。对专有名词、缩写（如型号、合同编号）容易吃亏，这是规划中的改进点。

### 3.2 检索效果不好，如何定位？

三个层面按顺序排查：

1. **Query 问题**：看日志里改写后的 `query` 是否偏离原意（`ChatService` 会记录 `Chat query='...' candidates=[距离列表]`）。若改写引入噪音，先修改写提示词或对无歧义问题跳过改写。
2. **Embedding 问题**：用“答案所在原文”当查询，若相似度仍然不高，说明 embedding 对领域术语表达弱，或查询与文档的表述风格差异大（口语 vs 书面语）。此时换/微调 embedding 或做查询扩展。
3. **索引问题**：确认 `embedding_model_version` 与当前模型一致，维度一致，`document_chunks` 中确有该文档切片且 `documents.status='READY'`。换过模型未重建索引是常见坑。

判断依据是召回的候选集合：正确答案不在 Top 10 里 → 召回问题（embedding/切块/query）；在 Top 10 但排不进 Top 3 → 重排问题；在 Top 3 但答错 → 生成/Prompt 问题。

### 3.3 有没有做重排序？用的什么模型？收益如何？

当前 `RerankService` 只是 `candidates.stream().limit(3)`，即按向量距离取前 3，**没有真正的语义重排**。这是当前实现里的明确占位，文档会如实标注为“待接入 DashScope rerank / bge-reranker”的改进项。

### 3.4 如何处理口语化、多轮对话中的指代消解？

`QueryRewriteService.rewrite()`：当有历史消息时，把最近 10 条历史与当前问题一起交给 LLM，要求“改写为独立完整的问题，只输出改写后的问题”，再拿改写结果去检索。

例如：

```
历史：作者是谁？→ 回答：张三
当前：他什么时候发表的？
改写：张三什么时候发表的？
```

这样“他”被展开，检索才能命中原文。改写失败或空白时回退为原问题。当前只做改写，不做显式实体抽取。

### 3.5 如何保证召回多样性，避免相似切片冗余？

当前没有做多样性控制：Top 10 里可能有大量来自同一段落、高度相似的切片，挤占重排名额。

这是明确的改进方向：在重排前对候选按“文档 + 段落”去重，或引入 MMR（最大边际相关）在相关性和多样性之间取平衡。MVP 阶段靠 Top 10 → Top 3 的截断把冗余限制在可接受范围。

## 四、生成与防幻觉

### 4.1 生成模型用哪个？上下文窗口多大？超长文档怎么处理？

当前生成模型为 `qwen3.7-plus`（`application.yml`），通过 Spring AI 的 OpenAI 兼容协议调用 DashScope；未配置 Key 时使用 `LocalChatModel` Mock。

上下文窗口未做硬性适配：每次生成只把最相关的 3 个切片（每个约 800-1200 token）+ 最近 10 条历史 + 当前问题拼入 Prompt，总量远小于模型窗口。超长文档不需要整篇塞进上下文，RAG 负责“只取出相关部分”。

### 4.2 如何让模型只根据检索内容回答，不编造？

三层约束：

1. **检索兜底**：Top 1 距离 > 0.65 或没有候选时，不调用生成模型，直接返回“文档中没有找到相关信息”；
2. **Prompt 约束**：System 消息固定为“你只能根据提供的文档内容回答；如果文档没有相关信息，回答‘文档中没有找到相关信息’；引用必须使用系统提供的编号 [1]..[3]；禁止自行生成不存在的编号”；
3. **引用校验**：生成后用 `CitationParsingService` 正则提取 `[n]`，只保留落在 `1..chunks.size()` 内的编号，模型编造的超范围编号被丢弃，前端也不会展示。

这套机制防的是“答非所问、无中生有”，不是绝对防幻觉；引用校验能挡住编造编号，但挡不住“内容真实但结论牵强”。后续方向是把检索块与答案逐句做 NLI/交叉编码器校验。

### 4.3 检索到的文档互相矛盾怎么办？

当前未实现显式矛盾处理。系统把每个切片连同文件名、页码一起交给模型，模型可以分别引用两处，但系统不强制它指出矛盾。

可接受的 MVP 行为是：模型依据两处原文分别说明，并引用两个来源。改进方向是加“矛盾检测”提示词策略（要求模型先判断来源是否冲突、分别陈述再给结论），或离线做来源一致性分析。

### 4.4 如何做引用/溯源？

闭环如下：

1. 检索出的切片按序编号 `[1]..[3]`，连同“文档名 + 页码 + 原文”写入 System 消息；
2. 模型回答中引用 `[n]`；
3. `CitationParsingService.parseAndValidate()` 提取并校验编号，只保留合法编号；
4. 每条合法引用写入 `answer_sources`（关联 message、chunk、document，记录 `relevance_score`，当前固定 1.0）；
5. SSE `done` 事件携带来源列表，前端 `SourceCard` 展示编号、文档名、页码和 120 字原文片段。

所以引用不是模型自由生成的链接，而是后端绑定到真实 chunk 的结构化数据。

### 4.5 如何防止 Prompt 注入或知识库内容干扰系统？

当前风险控制有限，需要如实说明：

- 文档内容作为上下文进入 System 消息，本质上属于“不可信内容”；恶意 PDF 可能尝试在文档里写“忽略以上指令”。
- 当前没有做指令边界标记或内容策略校验，也没有对检索文本做注入检测。

建议的轻量加固（尚未实现）：检索内容统一包在明确的分隔符/数据区中，系统指令与文档内容分离；对“忽略”“改指令”等模式做检测或提示模型只把检索内容当数据；引用校验保留，作为最后的兜底。

## 五、评估与迭代

### 5.1 如何评估 RAG？离线指标和线上指标是什么？

离线指标（`docs/acceptance/mvp-acceptance.md`）：

| 指标 | 定义 | 目标 |
|---|---|---|
| 答案正确率 | 人工判定与标准答案一致 | >= 85% |
| 引用准确率 | 引用存在且页码、原文正确 | >= 90% |
| 幻觉回答率 | 答案出现文档不存在的关键信息 | <= 5% |
| 无答案测试 | 文档无相关信息时必须返回固定文案 | 100% |
| 性能 | 20MB PDF 60 秒内 READY；问答 P95 < 10s、首字 < 5s | 通过 |
| 安全隔离 | 用户 A 访问用户 B 数据返回 404 | 通过 |

线上指标：`feedback`、`usage_logs` 表已建但当前未写业务数据，属于预留。后续应启用用户点赞/点踩、问答无答案率、引用点击率、平均首字延迟等。

### 5.2 如何构建评测集？

当前按“类别覆盖”构建：

- 固定 5 份测试 PDF：论文、技术文档、合同、行业报告、学习资料，每类 4 题，共 20 题；
- 每类按“核心方法/数据集/结论、安装步骤/配置/错误码、合同期限/违约/付款/争议、市场规模/驱动/玩家/风险、概念/公式/示例/练习答案”等模板出题；
- 每题准备标准答案，并记录答案对应的页码和原文片段，用于引用准确率判定；
- 额外准备“文档中不存在的信息”问题，测无答案兜底。

改进方向：用 LLM 辅助扩题、按难度分层、对检索层单独建“查询-相关段落”评测集（recall@k），与生成层解耦。

### 5.3 上线后效果下降，可能是什么原因？怎么持续优化？

常见原因：

1. 换了 embedding 模型但没重建索引，`embedding_model_version` 不匹配；
2. 文档内容更新了，但旧文档未删除或索引未重跑；
3. 查询分布变化（新领域、新表达），embedding 或切块策略不适配；
4. 相似度阈值在向量空间变化后不再合适；
5. 生成模型升级后行为漂移（更爱延伸、不再严格遵守“只根据文档回答”）。

持续优化闭环：先有线上反馈和日志（当前缺），才能持续调阈值、调切块、换重排模型。技术动作按优先级：接真实重排 → 混合检索 → 评测集扩大 → 反馈数据回流。

## 六、工程与性能

### 6.1 系统延迟大概多少？做了哪些优化？

当前没有生产环境的实测延迟数据，验收目标是“P95 问答 < 10 秒、首字 < 5 秒、20MB PDF 60 秒内 READY”。

已做的优化：

- 文档处理全异步（`@Async("documentTaskExecutor")`），上传接口立即返回，前端轮询状态；
- 问答用 SSE 流式返回（`SseEmitter`，120 秒超时），首字到达即可渲染，不用等完整答案；
- pgvector HNSW 索引支撑向量召回；
- 每次只把 Top 3 切片送入生成模型，控制 Prompt 长度和生成延迟。

未做的优化：连接池调优、embedding 批量/缓存、生成模型参数（temperature 当前 0.7）、CDN/静态资源等，属于规模化后再处理。

### 6.2 知识库更新频繁，索引如何更新？如何保证一致性？

当前是“文档级全量更新”：

- 新增/替换：重新上传，触发 `DocumentProcessingService` 全量解析 → 切块 → embedding → 写入 `document_chunks`；
- 删除：物理删除 `documents` 行，`document_chunks`、`messages`、`answer_sources` 由外键 `ON DELETE CASCADE` 级联清理，MinIO 原文件同步删除；
- 失败重试：处理失败时先删除已写入的 chunks，状态回退到 `UPLOADED`/`PENDING`，自动重试一次，再失败置为 `FAILED` 并保留错误信息。

一致性靠状态机保证：`documents.status`（UPLOADED → PROCESSING → READY/FAILED）和 `document_jobs.status`（PENDING → RUNNING → SUCCEEDED/FAILED）双表记录，检索只查 `status='READY'` 的文档，不会把半成品索引查出来。

局限：没有增量更新（改一页也要全文档重索引）、没有多副本/队列持久化（应用重启后正在处理的任务不会自动恢复）。这两个在任务量上来后再接队列（Kafka/RocketMQ）和增量索引。

### 6.3 多用户/权限隔离怎么做？

隔离是分层强制：

1. **认证**：JWT access token（内存保存，前端不写 localStorage）+ refresh token（HttpOnly Cookie，SHA-256 哈希入库）；
2. **数据访问**：所有查询带 `user_id` 过滤（`DocumentRepository.findByUserIdAndId`、`ConversationRepository.findByUserIdAndId`、`VectorIndexingService.searchWithContent(userId, ...)`）；
3. **项目隔离**：文档和会话挂在 `project_id` 下，控制器层校验项目归属；
4. **越权响应**：统一返回 404（不返回 403），避免泄露资源是否存在；
5. **文件隔离**：MinIO 对象 key 以 `userId/UUID.pdf` 组织，后端控制访问，不暴露公网 URL。

向量检索 SQL 同时带 `dc.user_id` 和 `d.project_id` 两个过滤条件，等于在检索层再做一次隔离。

## 七、开放对比题与未来方向

### 7.1 RAG 和长上下文模型相比，怎么看？什么时候用哪个？

不是替代关系，是按场景选：

- **RAG 更合适**：知识动态更新、内容私有、必须可溯源、文档可能超过上下文窗口、对单次推理成本敏感。智阅属于这一类。
- **长上下文更合适**：需要跨整本书做全局推理/总结、文档一次能塞下、不要求逐句引用、或内容高度相关不可切片。

实际系统通常是组合：RAG 负责召回相关片段，长上下文负责在召回片段上做深度推理。当前智阅只做了 RAG 部分。

### 7.2 RAG 未来优化方向

按当前实现从近到远：

1. **真实重排**：接入 DashScope rerank 或 bge-reranker，替代 `limit(3)` 占位；
2. **混合检索**：BM25 关键词 + 向量召回融合，解决专有名词/编号漏召；
3. **文档理解增强**：OCR、表格转 Markdown、版面分析，补齐扫描件和复杂 PDF；
4. **检索质量**：查询改写加强、MMR/去重、embedding 对比评测、检索与生成解耦的 recall@k 评测集；
5. **引用可信度**：答案逐句与来源做一致性校验、矛盾检测、`relevance_score` 从固定 1.0 改为真实评分；
6. **在线反馈闭环**：启用 `feedback`/`usage_logs`，用无答案率、点踩、引用点击驱动迭代；
7. **工程化**：异步队列、增量索引、多副本、监控告警。
