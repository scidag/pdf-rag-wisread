# 多类型文件处理链路分析：切片、向量化与存储

> 分析基准：`feat/wisread-mvp-phase1` 分支暂存区代码（含 V8 迁移后的多类型支持）。
> 覆盖类型：**PDF / DOCX / XLSX / TXT / MD**（见 `DocumentType` 枚举）。

---

## 一、端到端流水线总览

```
上传 (DocumentController POST /documents)
  │  校验扩展名 → 读取字节
  ▼
原件存储 (DocumentServiceImpl)
  │  MinIO: wisread-documents/{userId}/{UUID}{.ext}
  │  元数据: documents 表, status=UPLOADED
  ▼
异步流水线 (DocumentProcessingServiceImpl, @Async "documentTaskExecutor")
  │  ① 状态 UPLOADED→PROCESSING（job PENDING→RUNNING，原子抢占防并发）
  │  ② 清理旧向量（重试幂等）
  │  ③ MinIO 取回原件字节
  │  ④ DocumentParsingService.parse()  ← 按类型分发解析，输出统一 PageText 定位片段
  │  ⑤ ChunkingService.splitPage()     ← 统一切片（所有类型同一策略）
  │  ⑥ EmbeddingService.embed()        ← 批量向量化
  │  ⑦ VectorIndexingService.saveChunks() → pgvector 入库
  ▼
成功: status=READY，回写 page_count / token_count / embedding_model_version
失败: 清理向量 → 自动重试 1 次 → 仍失败 status=FAILED（errorMessage 展示给前端）
```

核心设计：**解析层按类型差异化，切片层及之后完全统一**。解析层把五种格式归一化为
`PageText(start, end, locationLabel, text)` 定位片段序列，后续分块/向量化/存储对类型无感知。

---

## 二、各类型解析方式（DocumentParsingServiceImpl）

解析层有两个共享参数：

| 参数 | 值 | 说明 |
|---|---|---|
| `TARGET_TOKENS` | 350 | 非 PDF 类型把小单元（段/行/表行）聚合成约 350 token 的定位片段 |
| `MAX_UNITS_PER_SEGMENT` | 120 | 单个聚合片段最多 120 个单元，防止单元极短时片段过大 |

为什么聚合：单个段落/表格行/文本行往往只有几十 token，直接作为向量粒度会过碎，
检索命中后上下文不完整；先聚合到约一个分块的大小，能显著提升召回质量。

### 1. PDF —— PDFBox 逐页抽取

- 实现：`PdfParsingServiceImpl`，`Loader.loadPDF` 加载 + `PDFTextStripper` 逐页抽文本
- 定位单位：**页**，`locationLabel = "页"`，每个 PDF 页 = 1 个定位片段
- 特殊处理：
  - **加密 PDF 直接 422**（无文本层权限）
  - **无 OCR 能力**：纯扫描件所有页文本为空 → 流水线判 422「scanned or empty document」
- `page_count` 语义 = 页数

### 2. DOCX —— Apache POI (XWPF) 按段落+表格行抽取

- 遍历 `bodyElements`：
  - `XWPFParagraph` → 取 `getText()`，空白丢弃
  - `XWPFTable` → **逐行**抽取，单元格用 `\t` 连接成一行文本
- 所有单元（段落+表格行）进入 `groupUnits(units, "段落")`，按 ~350 token 聚合成定位片段
- 定位单位：**段**（`locationLabel = "段落"`，start/end 为单元序号，非真实段落号）
- 损坏文件 422「corrupted or invalid DOCX」
- `page_count` 语义 = 段落/表格行的**原始单元总数**（非聚合后片段数）

### 3. XLSX —— Apache POI (WorkbookFactory) 逐工作表逐行抽取

- 每个工作表独立处理：
  - 单元格取值：`DataFormatter`（显示值）+ `FormulaEvaluator`（公式求值）
  - 一行 = 各非空单元格 `\t` 连接；整行空白跳过
  - **行聚合成 ~350 token 的片段**，片段携带 `startRow~endRow` 行号范围
  - `locationLabel = "工作表" + sheetName`（如「工作表Sheet1」）
- 定位单位：**工作表**（引用定位精确到「工作表X 第 n~m 行」）
- 损坏文件 422「corrupted or invalid XLSX」
- `page_count` 语义 = 工作表数量

### 4. TXT / MD —— 直接解码 + 按行抽取

- 解码优先级（`decode()`）：UTF-8 BOM → UTF-16 LE/BE BOM → **严格 UTF-8 校验** → 失败回退 **GB18030**（解决中文 TXT 乱码）
- 按 `\r?\n` 拆行，空行丢弃、每行 strip
- 进入 `groupUnits(lines, "行")` 聚合成 ~350 token 片段
- 定位单位：**行**（`locationLabel = "行"`）
- 注意：MD 的 Markdown 语法符号（`#`、`|`、`**` 等）**不做剥离**，原样进入切片
- `page_count` 语义 = 非空行总数

### 解析层差异矩阵

| 类型 | 解析库 | 定位单位 | locationLabel | pageCount 含义 | 类型特有处理 |
|---|---|---|---|---|---|
| PDF | PDFBox | 页 | 页 | 页数 | 加密 422、无 OCR |
| DOCX | POI XWPF | 段（单元序号） | 段落 | 段落+表格行总数 | 表格行 `\t` 连接 |
| XLSX | POI Workbook | 工作表内行号区间 | 工作表{name} | 工作表数 | 公式求值、按行聚合 |
| TXT | JDK Charset | 行序号 | 行 | 非空行数 | BOM/GB18030 解码 |
| MD | JDK Charset | 行序号 | 行 | 非空行数 | 同 TXT（语法不剥离） |

## 三、切片策略（ChunkingServiceImpl，全类型统一）

解析产出的每个定位片段独立切片，**不跨片段合并**（PDF 不跨页、XLSX 不跨工作表）。

| 参数 | 值 | 说明 |
|---|---|---|
| `MIN_CHUNK_TOKENS` | 300 | 低于此值不切，尽量保持语义完整 |
| `MAX_CHUNK_TOKENS` | 512 | 超过即切，避免超出 Embedding 上下文/稀释检索精度 |
| `OVERLAP_TOKENS` | 80 | 新块开头携带上一块尾部 80 token，保留跨块上下文 |

切片算法：

1. **归一化**：连续空白（含换行、全角空格）压缩为单空格 → *副作用：代码块缩进丢失*
2. **断句**：按中英文句末标点 `。！？.!?` 零宽断言切句，句子是拼接基本单元
3. **贪心累加**：三重条件才切新块——当前块非空 ∧ 加入本句超 512 ∧ 当前块已 ≥300
4. **重叠回填**：切分后取上一块尾部 ~80 token（按空格分词从尾累加）作为新块开头
5. 收尾剩余内容自然成块（句边界结束，可能 <300）

每个 `TextChunk` 携带：`content / pageStart / pageEnd / locationLabel / tokenCount`，
全局 `chunk_index` 由流水线维持连续递增。

> 设计意图（代码注释）：中文 1 字 ≈ 1 token（CJK 感知 TokenCounter），300~512 token
> ≈ 300~512 字的块粒度是召回精度与上下文完整性的平衡点；80 overlap 在小块下占比
> 合理（原 150 曾占 30~50% 被调小）。

## 四、向量化（EmbeddingServiceImpl）

| 项 | 值 |
|---|---|
| 模型 | `qwen3.7-text-embedding-flash`（DashScope，百炼专用端点） |
| 维度 | **1024**（显式锁定，与 `document_chunks.embedding VECTOR(1024)` 对齐） |
| 批大小 | 20 条/请求（`MAX_BATCH_SIZE`，切片按步长分批） |
| 调用方式 | Spring AI `EmbeddingModel.embed(batch)` |
| 用量统计 | 每批按 TokenCounter 估算输入 token 写入 usage_log（output=0） |
| 模型版本 | 随处理成功回写 `documents.embedding_model_version`，用于后续换模型时识别旧向量 |

注意：切片时已算过 token（分块累计），向量化阶段又为计费估算一次，两处独立。

## 五、存储层

### 1. 原始文件 —— MinIO

- Bucket：`wisread-documents`
- Key 规则：`{userId}/{UUID}{extension}`（如 `1/550e8400-...pdf`），用户前缀做逻辑隔离
- 上传时即写入（同步），处理流水线按 `fileKey` 取回字节
- 删除文档时同步删除 MinIO 对象

### 2. 文档元数据 —— PostgreSQL `documents` 表

关键字段：`file_type`（V8 新增，NULL 兼容旧 PDF 数据）、`file_key`、`page_count`、
`token_count`、`status`、`retry_count`、`error_message`、`embedding_model_version`。

状态机：`UPLOADED → PROCESSING → READY / FAILED`（重试时回退 UPLOADED）。
定时任务每 30s 回收卡死 job：PENDING 超 30s 重新调度、RUNNING 超时（默认 600s）回 PENDING 重排。

### 3. 切片与向量 —— PostgreSQL `document_chunks` 表（pgvector）

```
document_id / user_id        归属（双外键，级联删除）
chunk_index                  全文档连续序号
content                      切片文本
page_start / page_end        定位区间（页码/段序/行号/Excel 行号，随类型）
location_label               V8 新增：页 | 段落 | 工作表{name} | 行
token_count                  切片 token 数
embedding                    VECTOR(1024)，HNSW 索引 (vector_cosine_ops)
embedding_model_version      向量产生时的模型名
```

- 写入：`VectorIndexingServiceImpl.saveChunks`，逐条 INSERT，向量以 `PGobject("vector")`
  绑定 `[x,y,...]` 字面量（防注入）；写前先 `deleteByDocumentId` 清旧向量（重跑幂等）
- 检索：`<=>` 余弦距离升序 Top-N，**三重隔离**——`user_id`（租户）+ `project_id`（项目）+
  `status='READY'`（仅已完成文档）
- 引用回显：前端 SourceCard 用 `location_label` 渲染定位（如「第 3-5 页」「工作表Sheet1 第 1-20 行」）

## 六、全链路参数速查

| 环节 | 参数 | 值 |
|---|---|---|
| 解析聚合 | TARGET_TOKENS | 350 token/定位片段 |
| 解析聚合 | MAX_UNITS_PER_SEGMENT | 120 单元 |
| 切片 | MIN / MAX / OVERLAP | 300 / 512 / 80 token |
| 全文档 | MAX_TOKEN_COUNT | 500,000 token，超出 422 |
| 向量化 | 批大小 | 20 条 |
| 向量化 | 维度 | 1024 |
| 重试 | 次数 | 1 次（attempt 上限 2） |
| 调度 | 卡死恢复间隔 | 30s；RUNNING 超时 600s |

## 七、已知限制与潜在改进点

1. **无 OCR**：扫描版 PDF / 图片型内容一律 422，前端提示解析失败。
2. **XLSX 行文本丢失列头上下文**：行以 `\t` 值序列进入切片，第 2 行之后的数据行
   不带列名，孤立看难以判断语义（如「10-05 至 10-11 LLM API」）。可考虑每个片段
   首行拼上表头行。
3. **MD 语法符号未剥离**：`#`、表格 `|` 分隔符等原样进入向量文本；且归一化会压平
   代码块缩进。若 MD 是一等公民，可按 AST（标题/代码块）切片替代按行切片。
4. **切片不跨定位片段**：页尾/工作表尾的残句无法与下一页合并，会产生少量小块
   （<300 token 也照常入库），对召回略有稀释。
5. **逐条 INSERT 写向量**：大文档 chunk 多时写 入效率低（代码注释已说明是当前
   权衡），可改 JDBC batch。
6. **DOCX 定位序号是单元序号**而非可见章节号，引用定位对用户可解释性一般。
7. **旧数据兼容**：`file_type` 为 NULL 的旧文档按 PDF 兜底（`fromValueOrDefault`），
   预览与解析行为一致。
