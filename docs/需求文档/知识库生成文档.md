## 1. 项目背景与现状盘点

### 1.1 产品定位

智阅 WisRead 是一套 RAG 智能问答系统：用户上传多类型文档，系统自动完成"解析 → 分块 → 向量化 → 入库"的异步索引管道；问答时检索、生成流式回答，并附带引用溯源。当前形态为**单机部署、个人数据隔离**的可用产品。

**本模块（知识库管理）的目标**：将"文档/检索容器"从现有对话项目中**拆分为独立的知识库实体**，让用户能像管理个人资料库一样管理知识库——创建、上传、排障、调参、验证、发布的完整闭环；问答时自由选择知识库作为检索范围。

### 1.3 概念澄清：Project 当前承担的双重职责与拆分

现状 `Project` 实体（`entity/Project.java`）同时承担两个职责：

| 职责 | 现状表现 | 本模块处理 |
|---|---|---|
| A. 对话组织容器 | 会话创建/列表均挂在 projects 下（`ConversationController` 按 projectId 过滤） | **保留不动**，Project 继续作为对话项目 |
| B. 文档/检索容器 | 文档归属 projectId（`documents.project_id`）、检索按 projectId 过滤、上传入口在项目详情页 | **拆出为独立实体知识库（KnowledgeBase）**，文档、切片、检索配置、状态机全部挂载到知识库 |

拆分后的两个聚合根仅通过"问答选库"连接（见 2.2）：

- **对话项目（Project）**：用户围绕某主题发起的一组会话，回答时用户选择一个知识库作为检索范围；
- **知识库（KnowledgeBase）**：用户的个人文档资料库，可独立于任何对话存在，可被多个对话复用。

拆分收益：
1. 同一知识库可服务多个对话项目，文档不必重复上传；
2. 对话项目不再被迫"先建库传文档"，纯对话（不挂知识库）成为一等场景；
3. 知识库具备独立生命周期（状态机、归档、回收站），为后续共享、发布、联合检索打底。

## 2. 术语对齐与领域模型

### 2.1 术语对齐

后文需求描述用左列术语，API 与数据设计直接使用代码实体名：

| 本文档术语 | 代码实体 | 数据库表 | 含义 |
|---|---|---|---|
| 对话项目 | `Project`（现有，保留） | projects | 会话的组织容器，个人归属，支持软删除/回收站；**不再承载文档** |
| 知识库 | `KnowledgeBase`（P0-⓪ 新增） | knowledge_bases | 文档与检索的容器，个人归属，支持软删除/回收站/归档 |
| 文档 | `Document` | documents | 用户上传的一个文件及其索引状态记录；`project_id` 迁移为 `knowledge_base_id` |
| 切片 | `DocumentChunk` | document_chunks | 文档分块，含原文、页码区间、位置标签与向量 |
| 引用来源 | `AnswerSource` | answer_sources | 一条回答消息引用了哪个切片，含相关度得分（chunk 级，无需改动） |
| 会话 | `Conversation` | conversations | 项目内的连续问答上下文；新增可选 `knowledge_base_id` 表示当前选定的知识库 |
| 消息 | `Message` | messages | 会话内单条提问或回答 |
| 检索配置 | —（现为全局配置项） | —（挂到 knowledge_bases） | TopK / 相似度阈值 / Rerank 开关与 rerank-k |

### 2.2 领域模型（两个聚合根 + 选库连接）

```
┌─────────────────────────────┐         ┌──────────────────────────────────┐
│  对话项目 Project 聚合根      │         │  知识库 KnowledgeBase 聚合根       │
│  （现有，保留）               │         │  （P0-⓪ 新增）                    │
│                             │         │                                  │
│  ├── Conversations（会话）    │ 提问选库 │  ├── Documents（文档集合）         │
│  │     └── Messages          │ ──────▶ │  │     └── DocumentChunks（含向量）│
│  │           └── AnswerSources│  1..N  │  ├── RetrievalConfig（检索配置）   │
│  │                 ▲          │ 选定    │  ├── 状态机 DRAFT/PROCESSING/     │
│  └── 统计（会话数）            │ 知识库   │  │         ACTIVE/ARCHIVED        │
│                              │ 引用回链 │  ├── Members（成员）      [P1]    │
│                              │ ──────  │  ├── RetrievalEval（评估）[P1]    │
│                              │  chunk  │  └── Analytics（统计）    [P1]    │
└─────────────────────────────┘         └──────────────────────────────────┘
```

领域规则：
- **知识库与对话项目互不嵌套**：文档只能归属知识库，会话只能归属对话项目；
- 会话通过 `knowledge_base_id` 记录当前选定的知识库（可空 = 纯 LLM 对话，不检索）；
- **删除知识库 = 级联软删除其文档与切片的可见性**（回收站可恢复；与现有 projects 软删除语义对齐），彻底删除时才物理清理向量；
- 检索配置、成员、评估记录均**挂载在 KnowledgeBase 下**，不全局共享；
- AnswerSource 回链的是 chunk（documentId/chunkId），与知识库/项目解耦，**无需改动**。

### 2.3 知识库状态机（P0-⓪ 一并落地）

现状：Document 有状态机，知识库（及原 Project）无状态。知识库需要显式生命周期，支撑"发布"语义与知识库主工作流（见 3.4）：

```
DRAFT（新建，未发布）
   │ 上传文档后存在处理中文档
   ▼
PROCESSING（索引中，自动派生：库内存在 PROCESSING 文档）
   │ 全部文档就绪
   ▼
ACTIVE（正常，可被问答选用）◄──────────────┘
   │ 所有者显式操作
   ▼
ARCHIVED（归档：不出现在问答选库默认列表、禁止上传，已有会话仍可问答，可恢复；
          与回收站 deleted_at 互补）
```

- 状态存储：knowledge_bases 显式 `status` 字段；PROCESSING 由文档状态**派生计算**（文档状态变化时同步刷新），DRAFT→ACTIVE 首次自动，也可由所有者手动"发布"；
- 归档（ARCHIVED）与回收站（deleted_at）是两个正交维度：归档是业务休眠、可逆恢复，回收站是删除缓冲。

### 2.4 问答与知识库的绑定关系（第一版决策）

| 决策点 | 第一版方案 | 未来扩展 |
|---|---|---|
| 选库粒度 | **会话级**：创建会话时选择知识库（`conversations.knowledge_base_id`），会话内可切换（切换即改绑定） | 请求级覆盖（chat 请求带 knowledge_ids） |
| 单选/多选 | **单库** | 多库联合检索（P1-⑦，`knowledge_ids` ≤5） |
| 未选库 | **纯 LLM 对话**（不检索、无引用），UI 提示"选择知识库可基于文档回答" | 保持 |
| 检索过滤 | `user_id + knowledge_base_id + status='READY'`，越权库返回 403 | 成员可见性过滤（P1-⑧） |
| 归档库问答 | ARCHIVED 库**不出现**在选库默认列表，但已绑定该库的既有会话仍可继续问答 | 保持 |

> 理由：会话级绑定改动最小（ChatServiceImpl 现有"会话→检索范围"的单点替换），且与"用户在会话中选定一个资料库提问"的自然交互一致；请求级多选留到 P1，避免第一版同时改检索过滤 SQL 与前端选库 UI。

## 3. 差距分析：待实现需求分级

> 分级原则：**P0 = 用户直接感知、支撑"运营知识库"闭环的能力**（按 3.4 工作流串联）；P1 = 算法优化与协作扩展；P2 = 远期能力。

### 3.1 P0（本迭代必须）

**⓪ 知识库实体落地 + 存量数据迁移 + 问答选库**（一切后续功能的前置）

- **后端**：新增 `knowledge_bases` 表与 `KnowledgeBase` 实体/仓储/服务/控制器（CRUD 对齐现有 projects 能力：创建/列表/详情/更新/软删除/恢复/回收站/批量删除 ≤100，列表响应含文档数、切片数、状态）；`documents.project_id` → `documents.knowledge_base_id` 迁移（方案见 4.2）；检索过滤从 projectId 切换为 knowledgeBaseId。
- **问答选库**：`conversations` 增加 `knowledge_base_id`；创建会话时可选库、会话内可切换；`ChatServiceImpl` 检索范围改读会话绑定的知识库（校验库归属，越权 403）；未选库 = 纯对话不检索（放行现有 `projectId == null` 即报错的逻辑）。
- **前端**：新增独立"知识库"管理模块（导航入口）：知识库列表页 + 详情页（文档管理 / 状态徽牌 / 发布与归档）；问答面板（ChatPanel）增加知识库选择器；原项目详情页（ProjectSidebar）中的文档管理**迁出**至知识库模块，项目详情保留会话列表 + 问答；DocumentPreview 组件直接复用。
- **存量迁移**：现有含文档的对话项目 1:1 转为同名知识库，文档重指向（见 4.2 迁移方案），保证升级后用户数据无损、可回退。

**① 文档管理增强（批量上传 + 失败重试 + 状态可视化）**
- 批量上传：现仅单文件端点 `POST /api/v1/documents`，前端循环调用，任一失败即中断。需求：`POST /api/v1/documents/batch` 一次提交多文件，返回**逐文件结果**（成功/失败原因）。用户核心诉求："我上传失败怎么办？"
- 手动重新解析：`retryCount` 仅支持管道内自动重试 1 次，FAILED 后无人工干预入口，只能删除重传。需求：失败文档一键重试（清旧向量 → 状态复位 → 重走管道），需幂等保护（PROCESSING 中禁止重复触发）。
- 状态可视化：处理中文档在列表页自动轮询刷新（无需手动刷新页面）。
- 依赖：⓪；可复用单文件管道。

**② Chunk 查看**
- 现状：切片已落库（含页码、位置标签），但**无任何 chunk 读取 API**。
- 需求：知识库详情页中，文档可分页查看切片列表（content、chunkIndex、页码区间、位置标签、tokenCount）。
- 为什么重要：RAG 最大的问题不是模型，而是"**为什么搜不到**"——必须让用户能看到文档被切成了什么。
- 依赖：无，纯只读查询。

**③ RAG 测试页（Debug 控制台）**
- 现状：调参后没有任何地方验证效果，只能去正式问答里碰运气。
- 需求：知识库级调试控制台：输入测试问题 → 依次展示 **查询改写结果 → 向量召回列表（相关度/距离/页码）→ Rerank 结果 → 最终答案与引用**，并回显本次使用的检索配置与各阶段耗时。
- 依赖：⓪、④（读取知识库级配置）；与 ② 共用切片展示组件。
- 这是工作流"调整检索参数 → 测试问答"环节的落地，**没有它，检索配置就是盲调**。

**④ 知识库级检索配置**
- 现状：TopK（`wisread.retrieval.top-k`，默认 10）、rerank-k（默认 3）为全局 `@Value` 配置；拒答距离阈值 `DISTANCE_THRESHOLD=0.65` 硬编码在 `ChatServiceImpl`。所有库共享同一套参数。
- 需求：知识库详情页可配置 TopK / 相似度阈值 / Rerank 开关 + rerank-k；问答链路与 RAG 测试改为按会话所属知识库读取配置。
- **权限约束（第一版）：知识库所有者本人可修改**（个人隔离下即当前用户；越权库 403）。> 变更说明：V2.1 曾定为"仅 ADMIN 可改"，当时知识库隐含管理员运营语义；拆分为个人知识库后，配置权随库属，归所有者；P1-⑧ 引入成员共享后再收紧为 OWNER/EDITOR 分级。
- **配置优先级（第一版明确）：知识库级配置 > 系统默认（application.yml）。不引入用户级配置**；未来若引入，扩展为 用户 > 知识库 > 系统默认。
- 依赖：⓪（DDL 已随 knowledge_bases 建表一并落列，见 4.2），是 ③ 与 P1-⑤ 的前置。

**⑤ 知识库状态机**（DDL 随 ⓪ 落地，交互与验收单列）
- 状态派生规则（PROCESSING）、"发布"动作、归档/恢复、问答选库对 ARCHIVED 的处理，见 2.3。

### 3.2 P1（下一迭代：算法优化与协作扩展）

**⑤→⑥ 真实 Rerank 模型接入**
- 接入真实重排模型（cross-encoder 或 DashScope Rerank API），替换 `RerankServiceImpl` 的 `limit(rerankK)` 占位逻辑；失败时降级为占位截断并告警，问答不中断。
- 依赖：④（rerank_enabled / rerank_k 的读取位置）。

**⑦ 知识库统计仪表盘**
- 知识库维度统计页：Chunk 数、文档数、引用命中分布、token 用量趋势。原始数据已齐备（document_chunks / answer_sources / usage_logs），仅聚合展示。

**⑧ 多知识库联合检索**
- `POST /api/v1/chat` 支持请求级 `knowledge_ids` 数组（≤5），检索过滤改为 `knowledge_base_id IN (...)`；越权库返回 403。
- 依赖：若 ⑩（成员共享）先行，跨库"可见库"校验复用其权限逻辑；未落地前先支持自有库联合。

**⑨ 知识库成员共享 / 权限**
- knowledge_base_members 表（OWNER / EDITOR / VIEWER 三档）；影响面最大：全链路 user_id 过滤改造（检索、CRUD、上传、选库），需单独排期回归。检索配置权限随之收紧为 OWNER/EDITOR。

**⑩ RAG 质量评估（Retrieval Evaluation）**
- 痛点：系统已有 Citation / Rerank / Vector，下一步必然遇到"**为什么回答质量不好？**"。没有评估数据，调优无从下手。
- 需求：记录全链路评估数据：`query → 改写 → 召回 chunks（含距离）→ rerank 结果 → 最终引用 → 用户反馈（👍/👎）`；管理端展示拒答率、引用命中率（回答含 ≥1 引用比例）、反馈分布、7 天趋势；为后续命中率 / Recall@K / MRR 指标打基础。
- 依赖：弱依赖 ③（复用调试链路的阶段数据结构）。

**⑪ 文档版本管理（可选，后置）**
- documents 加 version、版本链与回滚，检索默认命中最新版本；与 ⑨ 的检索过滤改造有交集，建议同轮统筹。

### 3.3 P2+（远期，见第 8 章）

URL 采集 / 网页爬虫、OCR、Hybrid Search（BM25 + 向量）、知识图谱、Agent / 工作流。

### 3.4 知识库主核心工作流（UI 与原型组织依据）

原型与页面设计必须围绕此流程组织，**避免"堆功能"**：

```
① 创建知识库（DRAFT）                       —— 知识库列表页
        ↓
② 批量上传文档（P0-①）
        ↓
③ 等待处理（PROCESSING，进度可视化，自动轮询）
        ↓
④ 处理失败文件（查看 errorMessage → 重新解析，P0-①）
        ↓
⑤ 抽查切片（Chunk 查看：内容/页码/token，P0-②）
        ↓
⑥ 调整检索参数（所有者可改，P0-④）
        ↓
⑦ RAG 测试验证（Debug：召回 → 重排 → 答案 → 引用，P0-③）
        ↓
⑧ 发布（ACTIVE）→ 到对话里选择该知识库提问（P0-⓪ 选库交互）
```

场景示例：HR 上传员工手册 → 创建"HR 知识库" → 批量上传 10 个文件 → 1 个失败点击重试 → 抽查切片确认切分合理 → 调整 top_k=15 → 测试页验证召回与答案 → 发布 → 在任意对话中选中"HR 知识库"提问。

### 3.5 依赖关系

```
⓪知识库实体+迁移+选库 ──→ ①②④⑤（挂载点切换）──→ ③RAG测试页（读取④配置）──→ ⑥真实Rerank（P1）
⓪问答选库（独立可并行于①②④）
⑩质量评估（弱依赖③的阶段数据结构）
⑨成员共享 ──→ ⑧联合检索（可见库校验复用）
⑪版本管理 ──↔ ⑨（检索过滤改造交集，同轮统筹）
⑦仪表盘（弱依赖①②）
```

ALTER TABLE documents

**决策三：存量迁移四阶段（增量、可回退，对齐现有部署习惯）**

| 阶段 | 动作 | 回退方式 |
|---|---|---|
| A 加法 | 建 knowledge_bases 表 + documents/conversations 加列；旧代码不读新列，线上行为不变 | 无需回退（纯加法） |
| B 回填 | 迁移脚本（Flyway）：① 每个含文档的 project 生成 1 个同名 ACTIVE 知识库（含 legacy_project_id 映射，幂等防重）；② `documents.knowledge_base_id = 映射表(kb.legacy_project_id = documents.project_id)` 回填；③ 已有会话按其 project 映射初始化 `conversations.knowledge_base_id`（保证老用户问答行为无缝） | 映射可重放；新旧列并存，回退即切回旧列 |
| C 切换 | 代码切换：检索过滤/上传参数/列表查询改读 knowledge_base_id；发布知识库管理页与问答选库 UI | 应用回滚至上一版本即回读 project_id（数据未破坏） |
| D 清理 | 验证一个发布周期后：DROP documents.project_id、knowledge_bases.legacy_project_id，CHANGE SET 记录迁移完成 | 依赖备份快照 |

回填 SQL 示意（实际以 Flyway 脚本 + 幂等守卫为准）：

```sql
INSERT INTO knowledge_bases (user_id, name, description, status, legacy_project_id, created_at, updated_at)
SELECT p.user_id, p.name, p.description, 'ACTIVE', p.id, now(), now()
FROM projects p
WHERE p.deleted_at IS NULL
  AND EXISTS (SELECT 1 FROM documents d WHERE d.project_id = p.id)
  AND NOT EXISTS (SELECT 1 FROM knowledge_bases kb WHERE kb.legacy_project_id = p.id);

UPDATE documents d
SET knowledge_base_id = kb.id
FROM knowledge_bases kb
WHERE kb.legacy_project_id = d.project_id AND d.knowledge_base_id IS NULL;

UPDATE conversations c
SET knowledge_base_id = kb.id
FROM knowledge_bases kb
WHERE kb.legacy_project_id = c.project_id AND c.knowledge_base_id IS NULL;
```

**决策四：检索过滤切换后的 SQL 形态**

```sql

-- 切换后（单库）
WHERE c.user_id = ? AND d.knowledge_base_id = ? AND d.status = 'READY'
-- P1-⑧ 联合检索
WHERE c.user_id = ? AND d.knowledge_base_id IN (?, …) AND d.status = 'READY'
```

## 6. 非功能需求与技术栈

### 6.1 技术栈（对齐现状，单机部署）

- 后端：Spring Boot 3 + Spring AI + MyBatis-Plus
- 数据库：PostgreSQL + pgvector（向量内嵌于业务表，无独立向量库）
- 缓存/会话：Redis（登录会话 ZSET 索引、限流）
- 对象存储：MinIO（bucket：wisread-documents）
- 模型：DashScope Embedding（1024 维）+ LLM 流式生成；Rerank 待接入（P1）
- 前端：Next.js 15 App Router + React 19 + Tailwind 3.4，SSE 流式输出
- 可观测：Micrometer 指标 + usage_logs / chat_logs 审计

### 6.2 性能指标（务实，匹配单机与并发 8 的现实）

- 文档上传接口同步部分 P95 < 1s（解析/索引全异步）；批量上传 10 文件请求 P95 < 3s（仅入队）；
- 单文档索引（<50 页）P95 < 60s，状态轮询可见；
- 问答端到端 P95 < 10s（对齐 `wisread.chat.slow-threshold-ms:10000`），TTFT P95 < 3s；RAG 测试页复用问答链路，同指标；未选库纯对话跳过检索阶段，端到端相应缩短；
- 并发问答上限 8（信号量，超限排队计入 `wisread.chat.queue.wait`）；
- 向量检索（单库万级 chunk，TopK 余弦排序）< 200ms；Chunk 分页查询 P95 < 300ms；
- 迁移阶段检索过滤由 project_id 改为 knowledge_base_id，查询计划需复核索引（documents(knowledge_base_id, status) 组合索引建议在阶段 A 一并创建）。

### 6.3 安全（沿用现有约定）

- JWT：typ=JWT，secret-current 签发校验 / secret-previous 仅校验；access-token 15m，refresh 绝对有效期 24h；
- 限流：Redis 实现，问答接口受并发信号量保护；
- CORS：白名单（默认 localhost:3000）；
- 数据隔离：全接口按 user_id 过滤；**新增"选库越权"校验**——会话绑定的知识库必须属于当前用户（或 P1-⑨ 后为成员可见库），否则 403；
- 上传限制：单文件 100MB / 单请求 110MB，类型白名单（DocumentType）；
- 权限：知识库检索配置 PATCH、RAG 测试仅限所有者本人（P0 新增约束；P1-⑨ 后按成员角色分级）。

> 开发与测试逐条对照执行，避免"实现了但没有验收口径"。

**P0-⓪ 知识库实体 / 迁移 / 问答选库**

- Given 存量用户 A 的项目 P1 内已有 5 个文档（部分 INDEXED），When 执行迁移脚本，Then 自动生成同名 ACTIVE 知识库，5 个文档全部重指向且状态/向量不变，A 的既有会话自动绑定该库，问答行为与迁移前一致；
- Given 用户创建知识库"产品手册"，When 查看列表，Then 出现该库且状态 DRAFT、文档数 0；
- Given 用户在对话中未选择知识库提问，When 提交问题，Then 走纯 LLM 对话（无检索、无引用、不拒答），回答正常流式输出；
- Given 会话已绑定知识库 KB1，When 切换为 KB5（他人库），Then 返回 403"无权访问该知识库"，绑定不变；
- Given 会话绑定 ARCHIVED 知识库，When 继续提问，Then 仍可基于该库检索回答（选库列表中不再出现该库）。

**P0-① 文档管理增强**

- Given 用户选择 3 个文件（pdf/docx/md）提交批量上传，When 请求完成，Then 返回逐文件结果：成功文件状态 UPLOADED 进入队列，失败文件展示中文原因，任一失败不影响其他文件；
- Given 文档状态为 FAILED，When 点击"重新解析"，Then 返回 202，旧向量清理、状态复位 PROCESSING，完成后变 INDEXED；
- Given 文档状态为 PROCESSING，When 再次点击"重新解析"，Then 返回 409 并提示"文档处理中，请勿重复操作"；
- Given 文档列表存在 PROCESSING 文档，When 页面停留，Then 状态徽牌 ≤5s 自动轮询刷新，完成后无需手动刷新即变 INDEXED。

**P0-② Chunk 查看**

- Given 一个 PDF 已完成索引（status=INDEXED，312 块），When 点击"查看切片"，Then 分页展示切片，每条包含 content、chunkIndex、pageStart/pageEnd、locationLabel、tokenCount；
- Given 切片超过 20 条，When 翻到第 2 页，Then 返回 page=2 的 20 条且 total=312 正确；
- Given 文档未完成索引，When 请求 chunks，Then 返回空列表并附当前状态。

**P0-③ RAG 测试页**

- Given 用户在 ACTIVE 知识库测试页输入问题并运行，Then 依次展示：改写后查询、召回列表（含文档名/页码/距离）、Rerank 结果（标注占位实现）、最终答案与引用，并回显 used_config 与各阶段耗时；
- Given 检索配置 top_k 从 10 改为 20 并保存，When 重跑同一问题，Then 召回条数与 used_config.top_k 一致；
- Given 测试问题与库内内容完全无关，When 运行测试，Then 全部距离超阈值，展示"拒答（相似度不足）"而非编造答案。

**P0-④ 知识库级检索配置**

- Given 所有者修改 top_k=15、rerank_enabled=false 并保存，Then 保存成功，该库后续问答与测试读取新配置，其他库不受影响；
- Given 用户 B 访问用户 A 的知识库配置接口，Then PATCH 返回 403"无权修改该知识库的检索配置"，GET 同样 403（个人隔离）；
- Given rerank_k=5 且 top_k=3，When 保存，Then 校验失败提示"rerank_k 不能大于 top_k"。

**P0-⑤ 知识库状态机**

- Given 新建知识库，Then 状态为 DRAFT；上传文档后存在处理中文档时展示 PROCESSING；全部就绪后为 ACTIVE（或手动发布）；
- Given 所有者归档知识库，Then 问答选库默认列表不再展示（可在归档筛选中找到），该库禁止上传，既有绑定会话仍可问答，可恢复。

**P1-⑥ 真实 Rerank**

- Given rerank_enabled=true 且模型可用，When 提问，Then 召回 top_k 条经重排取前 rerank_k 条进入上下文，新增 rerank 耗时指标；
- Given 重排模型调用失败，When 提问，Then 自动降级为占位截断并记录告警，问答不中断。

**P1-⑩ 质量评估**

- Given 一条回答完成，When 用户点击 有用/无用，Then 反馈落库并与该消息的召回、引用记录关联；
- Given 用户查看评估报表，Then 可见拒答率、引用命中率、反馈分布及 7 天趋势。
